03 · The finding that sets the order of work

Restarting Elephant kills your browser

systemd reports 1.2 GB for elephant.service (peak 2 GB, 431 tasks). Elephant itself holds 30 MB. The rest is twelve Helium processes, about 2.3 GB RSS, sitting in Elephant's cgroup.

The cause is one line in walker.nix: auto_detect_launch_prefix = false. With no prefix, Elephant launches with sh -c and Setsid. setsid detaches the terminal session but leaves the process in the unit's cgroup, and the unit uses KillMode=control-group. The Walker and Elephant Home Manager modules also attach X-Restart-Triggers hashed over the whole config, and walker.service has Requires=elephant.service. Any edit to the launcher config therefore restarts Elephant on switch and takes your Walker-launched apps with it. That is the mechanism behind the AGENTS.md rule about not auto-restarting these units.

A naive launcher would just move the bug from Elephant into the shell.

systemd-run --user --scope --collect --quiet \
  --slice=app.slice --unit=app-stillsuit-<desktop-id>-<rand> \
  -- <argv from DesktopEntry.command>

05 · Architecture

Where each piece lives

The host contract gives plugins no process runner, and payloads never become argv. So the launcher's providers return typed intents, and the core executes them through new named actions. The view stays a view. The service owns state, history and async processes.

Why a core MenuHost and not a window the plugin owns? Today the router hosts only panels. A menu instance gets no window, so the OSD plugin builds its own. A plugin-owned window would hot-reload, but clipboard, a future emoji grid and dmenu would each copy the layer-shell, focus and dismiss logic. One host keeps panel exclusion and output choice in a single place, at the cost of one rebuild.

    07 · Provider contract

    Providers return intents, the core runs them

    Each provider is a .pragma library JS file with no QML imports, so node can load it in tests. Sync providers answer inside the keystroke. Async ones (calc, files) hand the service an argv to run, and the service drops any reply whose generation number is stale.

    // providers/apps.js
.pragma library
const meta = { id: "apps", label: "Applications", prefix: "", kind: "sync" }

function query(text, env) {
  // env.apps: snapshot of DesktopEntries, env.match: Matcher.score, env.usage: History.boost
  return env.apps.map(app => ({
    key: app.id, text: app.name, subtext: app.genericName, icon: app.icon,
    ...env.match(text, [app.name, app.genericName, app.keywords.join(" "), app.comment], app.id),
    actions: ["launch", ...app.actions.map(a => "action:" + a.id)],
  })).filter(r => r.score > 0)
}

function activate(item, action) {
  return action.startsWith("action:")
    ? { type: "app.launch", desktopId: item.key, actionId: action.slice(7) }
    : { type: "app.launch", desktopId: item.key }
}

    08 · Search and ranking

    Elephant's scoring, Omarchy's acronyms, your history

    • Fuzzy match. fzf-style subsequence scoring. Bonuses for string start, word boundaries, camelCase and consecutive runs; penalties for gaps and late starts. Same idea as Elephant's FuzzyMatchV2 with score − start. Returns match positions for highlighting.
    • Field weights. Each field after the first costs min(index × 5, 50), as in Elephant. For apps that means name, then generic name, keywords, comment.
    • Acronyms. For terms of 5 characters or fewer, also match first letters of words and camelCase parts, as Omarchy's AppSearch.js does.
    • Usage boost. Port of Elephant's CalcUsageScore: per (query, item) a count capped at 10 and a last-used date; max((10 − days) × count, 1) over the length difference between the stored and current query. It's added only once an item has passed the minimum score. Stored at $XDG_STATE_HOME/stillsuit/launcher/history.json with atomic writes. The old gob history can't be read and starts empty. It's 4 KB, so little is lost.
    • Order. Score descending, then text. Results capped at 100, your current max_results.

    11 · Decisions

    What I settled, and what I need from you

    Settled unless you object

    • A core MenuHost rather than a window inside the plugin. That costs one rebuild and saves copying the same window logic into every future picker.
    • Typed intents only. The one place a raw command runs is > mode, from your keyboard.
    • The window switcher lists most recently focused first, using niri's focus_timestamp. Walker uses toplevel order.
    • Same keys at cutover, no dmenu in v1, history starts fresh.
    • Clipboard is its own plugin, so a profile can switch it off without losing the launcher.

    Questions

    1. Replace Elephant as well as Walker?

    Recommended: yes.

    The alternative is to keep Elephant as the backend and talk to its socket in JSON mode (format byte 1, no protobuf). That would shrink P1, but you keep a daemon whose development is on hold, an unpatched clipboard deadlock unless you bump the pin, and the cgroup fix as a launch_prefix setting instead of something Stillsuit guarantees.

    2. Clipboard retention.

    Recommended: keep today's 200 items with no expiry, and add the password-manager skip.

    That matches your current setup (max_items = 200, auto_cleanup = 0). The other choice is an age limit, for example 7 days, with images deleted sooner.

    3. Which prefix modes do you actually use?

    Default: build all of them in P2.

    Runner and web search have history files, so you've used those at least. If / files, . symbols or ; provider list never come up, P2 gets shorter.
