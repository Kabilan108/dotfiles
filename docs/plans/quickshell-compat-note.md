# Quickshell 0.3.0 compatibility audit for the Omarchy Quattro port

Audited upstream tag `v4.0.0`, commit `f0020448ca87329199de7cb12f2015ebc4a3e5e7`, against local `Quickshell 0.3.0 (revision tag-v0.3.0, distributed by Nixpkgs)`. The installed executable is `/nix/store/ryfyyhn3xnx3nwbknjl6kihxfkzc6w5m-quickshell-0.3.0/bin/quickshell`. All installed metadata citations below are under that store path.

## 1. Verdict

**OK-with-workarounds.** Quickshell 0.3.0 contains every Quickshell QML module, type, property, signal, and method used by the architectural patterns in Quattro's shell. The composition root, dynamic QML loading, registry scan, IPC handlers, per-output surfaces, file and process APIs, and imported system service APIs can be ported. There is one confirmed operational incompatibility. Quattro's restart command requires a newer `quickshell-git` change that makes `quickshell kill` wait for the selected instance to exit. In 0.3.0 it returns immediately, so the exact kill-loop-then-launch sequence can race a dying instance. Stillsuit must provide its own process-exit barrier or let systemd perform the stop and start. Quattro also contains Hyprland-only code. That is a compositor-porting issue, not a missing 0.3.0 API, and it must stay behind the Niri adapter.

## 3. Specific incompatibilities

### Confirmed incompatibility

| API or behavior | Upstream dependency | 0.3.0 evidence | Workaround |
|---|---|---|---|
| `quickshell kill` completion | `/vault/repos/omarchy-quattro/bin/omarchy-restart-shell:64-67` says each kill must stop the oldest matching instance and return only after full exit so the replacement cannot race it. The same file says this requires Quattro's `quickshell-git` build because 0.3.0 returns immediately. `/vault/repos/omarchy-quattro/migrations/1784672586.sh:1-7` installs `quickshell-git` for this reason. | The installed 0.3.0 CLI supports selecting by `--id`, `--pid`, `--path`, `--config`, oldest or default versus `--newest`, and `--any-display`, but the package does not supply a completion barrier. The decisive version comparison is the pinned upstream migration and restart-script comment. | Do not copy the kill loop. Prefer a user systemd service and `systemctl --user restart`, which orders stop completion before start. If invoking the CLI directly, resolve the selected PID first, issue `quickshell kill`, then wait until that PID no longer exists with a bounded timeout before launching. Do not use a fixed sleep. |

### Loaders and dynamic construction

- Quattro uses standard Qt `Loader`, not Quickshell `LazyLoader` or an `AsyncLoader`, for its selectable bar. It sets `active`, `source` or `sourceComponent`, and `asynchronous`, and observes `loaded`, `activeChanged`, and `status`; see `/vault/repos/omarchy-quattro/shell/shell.qml:237-260`. These are Qt Quick loader contracts, not a newer Quickshell API.
- Service components use `Qt.createComponent(url, Component.PreferSynchronous)`, handle `Component.Loading`, connect `statusChanged`, then call `createObject`; see `shell.qml:283-320`. Bar widget components use `Component.Asynchronous`, the same status state machine, and registry insertion only after `Ready`; see `shell.qml:788-811`. This is Qt's component API and works with the Qt bundled with the local Quickshell build.
- 0.3.0 also exports `LazyLoader.item`, `loading`, `active`, and `activeAsync` at `.../Quickshell/quickshell-core.qmltypes:538-590`. Stillsuit already uses `LazyLoader`, so it is locally proven. Quattro itself does not depend on it.
- Quattro's plugin-bar error handler calls `errorString()` conditionally at `shell.qml:254-258`. `errorString()` belongs to `QQmlComponent`, while the standard Qt Quick `Loader` contract exposes `status` but not a documented `errorString()` method. Treat the diagnostic string as non-portable. The fallback state update must not depend on that expression completing. Log the URL and status, or use explicit `Qt.createComponent` when detailed compile errors are required.

### Registry, file IO, and component caching

- `PluginRegistry.qml` does not scan with `FileView`. It runs `bash` and `find` through `Process`, collects stdout with `StdioCollector { waitForEnd: true }`, creates the user directory through another `Process`, and runs recursive `inotifywait` through a long-lived `Process` plus `SplitParser`; see `/vault/repos/omarchy-quattro/shell/services/PluginRegistry.qml:618-698`. 0.3.0 provides writable `Process.running`, `command`, stdout and stderr parsers, `exited`, `exec`, `signal`, and `write` at `.../Io/quickshell-io.qmltypes:48-191`.
- Dynamic entry points are sanitized as relative paths in `PluginRegistry.qml:36-41` and resolved to file URLs by registry code before the host calls `Qt.createComponent`; service loading is at `shell.qml:283-320`, widget loading at `:788-811`. No newer Quickshell dynamic-instantiation helper is involved.
- Hot reload unloads panels, services, and widget registrations, defers one event-loop turn, calls `Qt.clearComponentCache()` if present, and rescans; see `shell.qml:734-778`. It does not call `trimComponentCache`, `Quickshell.reload`, or an upstream-only cache API. `Quickshell.reload()` does exist in 0.3.0 at `.../Quickshell/quickshell-core.qmltypes:1035-1039`, but the planned per-plugin reload should not use it because that would reload the entire shell engine.
- Config persistence uses `FileView.setText()` with `atomicWrites: true`; see `shell.qml:108-113`, `:130-139`. File watching uses `watchChanges`, then calls `reload()` from `onFileChanged`; see `:117-139`. 0.3.0 exposes `atomicWrites`, `watchChanges`, `loaded`, `loadFailed`, `saved`, `saveFailed`, `fileChanged`, `reload`, and `setText` at `.../Io/quickshell-io.qmltypes:300-505`. Preserve the explicit `onFileChanged: reload()` contract. A watch event does not by itself promise that `text()` has been refreshed.

### IPC and instance selection

- Quattro declares ordinary typed `IpcHandler` functions. The image selector is at `/vault/repos/omarchy-quattro/shell/shell.qml:821-868`; the generic shell lifecycle API starts at `:872-919`. 0.3.0 exports `IpcHandler.enabled` and `target` at `.../Io/quickshell-io.qmltypes:568-602`. Stillsuit already uses multiple `IpcHandler` objects successfully.
- The wrapper calls `qs ipc -n -p "$OMARCHY_PATH/shell" call -- <target> <method> ...`; see `/vault/repos/omarchy-quattro/bin/omarchy-shell:55-75`. In this subcommand, `-n` selects the newest matching instance. The `--` protects function names that resemble subcommands. 0.3.0 supports `ipc call`, target and method arguments, path or config selection, instance ID or PID selection, newest selection, and display filtering. No newer IPC feature is required by the host contract.
- `quickshell -c <name>` names a configuration, not an arbitrary caller-chosen instance ID. Quattro launches with `-n -p "$OMARCHY_PATH/shell"`; see `/vault/repos/omarchy-quattro/bin/omarchy-launch-shell:17-20`. It selects later operations by the same path. 0.3.0 exposes generated `instanceId` and config-derived `shellId` properties at `.../Quickshell/quickshell-core.qmltypes:891-908`. Keep config identity and runtime instance identity distinct in the Stillsuit contract.

### Per-output surfaces and popups

- Quattro creates one notification `PanelWindow` per `Quickshell.screens` entry with `Variants`; see `/vault/repos/omarchy-quattro/shell/plugins/notifications/Service.qml:946-964`. Backgrounds use the same pattern at `plugins/background/Background.qml:181-218`. 0.3.0 exposes the screen list and `Variants.model` as cited in the module table, and `PanelWindow` screen, mask, and window state in `.../Quickshell/_Window/quickshell-window.qmltypes:620-770`.
- The used WLR enums and attached properties are all present. `WlrLayer` values and `WlrKeyboardFocus.None`, `Exclusive`, and `OnDemand` are at `.../Wayland/_WlrLayerShell/quickshell-wayland-layershell.qmltypes:10-39`; `layer`, `namespace`, `keyboardFocus`, `exclusiveZone`, and `exclusionMode` are at `:42-134`. Quattro uses `ExclusionMode.Ignore` for overlays and a non-ignored exclusion mode for its bar. Stillsuit already proves the same `PanelWindow` and WLR properties on Niri.
- Quattro uses `PopupWindow` indirectly through `Ui/PopupCard.qml:6` for bar-anchored popups and directly in `plugins/bar/Bar.qml:1041`. 0.3.0 exports `PopupWindow` and its anchor and window properties in `.../Quickshell/_Window/quickshell-window.qmltypes:620-770`. Keyboard-heavy panels deliberately use full `PanelWindow` surfaces instead of xdg popups; `Ui/KeyboardPanel.qml:10-21` explains that choice. Preserve that split.

### System integration APIs

- Pipewire, UPower, Mpris, Bluetooth, Networking, Notifications, SystemTray, Pam, and Polkit all ship in the installed 0.3.0 module tree and expose the exact members Quattro calls, as detailed in the table.
- Quattro does not import a Quickshell NetworkManager service under `Services`. It uses the incubating `Quickshell.Networking` backend directly; see `/vault/repos/omarchy-quattro/shell/plugins/panels/network/Panel.qml:4-6`, `:68-71`, and `:206`. The same API exists in 0.3.0 at `.../Networking/quickshell-network.qmltypes:202-214`, `:360-426`.
- Hyprland imports are present in the installed package, but their behavior depends on Hyprland. They are not valid Niri fallbacks merely because QML can resolve the imports.

### Path helpers

- Quattro calls `Quickshell.env()` throughout and logs `Quickshell.shellDir` at `/vault/repos/omarchy-quattro/shell/shell.qml:141-147`. 0.3.0 exposes `shellDir`, `configDir`, `dataDir`, `stateDir`, `env`, and `workingDirectory` at `.../Quickshell/quickshell-core.qmltypes:937-1045`.
- Quattro does not use `dataDir` or `stateDir`. Its persistent paths are built from `HOME`, `XDG_STATE_HOME`, or `OMARCHY_PATH`, for example `plugins/agents/Main.qml:15-16`. For Stillsuit, inject resolved config, data, and state roots through `HostContext` or use 0.3.0's helpers consistently. Do not let plugins invent a mixture of both conventions.

## 4. Restart/reload semantics

Quattro has two separate reload mechanisms.

1. **In-process plugin and config reload.** File changes in the mutable local plugin directory trigger `inotifywait`, a 150 ms timer, staged destruction of plugin objects, `Qt.clearComponentCache()`, a registry rescan, then reconstruction; see `/vault/repos/omarchy-quattro/shell/services/PluginRegistry.qml:636-659` and `/vault/repos/omarchy-quattro/shell/shell.qml:739-778`. Config `FileView` objects hot-reload their JSON at `shell.qml:117-139`. These mechanisms are compatible with 0.3.0.
2. **Whole-shell restart.** The launcher disables Quickshell's own source watcher with `QS_DISABLE_FILE_WATCHER=1` and `QS_NO_RELOAD_POPUP=1`; see `/vault/repos/omarchy-quattro/bin/omarchy-launch-shell:13-20`. The restart script drains all path-matching instances with repeated `quickshell kill`, then launches one replacement; see `bin/omarchy-restart-shell:64-74`. This exact ordering is not compatible with 0.3.0 because its kill returns before exit. Quattro changed its package from release `quickshell` to `quickshell-git` specifically to gain synchronous completion; see `migrations/1784672586.sh:1-7` and `install/omarchy-base.packages:111`.

The 0.3.0-safe contract is simple. Systemd owns the process. In-process reload owns only plugin objects. Whole-shell replacement uses systemd's ordered restart or an explicit PID-exit wait. IPC readiness is a second barrier after process start. Quattro polls `shell ping` after launch at `bin/omarchy-restart-shell:73-91`; retain that readiness check instead of equating a live PID with a ready plugin registry.

## 5. Contract implications

- Keep manifest loading independent of the Quickshell source watcher. Use explicit states such as `unloaded`, `loading`, `loaded`, and `error`. 0.3.0 provides the necessary component and loader states, but Quattro's current registry records failures separately instead of exposing a complete state object.
- Make dynamic construction asynchronous-capable. A manifest entry point may return no object on the initiating call while its `QQmlComponent` is `Loading`; Quattro's service path already does this at `shell.qml:294-320`.
- Keep the `QQmlComponent` alive for every registered widget. Quattro stores it in `pluginWidgetComponents` at `shell.qml:781-811`; the manifest and loader contract should make that ownership explicit.
- Abstract config, data, state, and package roots in `HostContext`. 0.3.0 has helpers, but Quattro's plugins assume Omarchy environment variables and mutable home-directory paths. Store-backed Nix plugins must not inherit those assumptions.
- Keep compositor services out of the portable host contract. `Quickshell.Hyprland` exists in 0.3.0, but focus grabs, workspace access, and Hyprland IPC do not work on Niri. Supply narrow Niri-owned interfaces where a plugin genuinely needs them.
- Define per-output scope in the manifest. Services and registries remain global; `Variants` creates output views. Do not instantiate a global notification, media, or registry service once per screen.
- Do not expose raw whole-shell `kill` as a plugin lifecycle operation. Plugins may request unload, reload, or rescan through IPC. The systemd unit owns whole-process replacement and the exit barrier.
- Treat IPC config selection and instance identity separately. Use one canonical Stillsuit config path or name, generated runtime instance IDs for diagnostics, and a readiness method. Avoid choosing "newest" as the normal correctness mechanism once systemd guarantees a single instance.
- Preserve explicit file reload semantics and serialize writes. `atomicWrites` protects replacement of one file, but it is not a multi-writer transaction or a plugin trust boundary.
